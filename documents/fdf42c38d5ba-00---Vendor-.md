# Vendor 軟體銷售導讀

這份導讀只使用兩種已經落盤的輸出。

- 金額與回歸：`analysis/regression_results.json`，由 `analysis/vendor_regression.py` 用 openpyxl 讀週報儲存格快取。
- 贏單組合：`analysis/combo_results.json`，由 `analysis/vendor_combo_distribution.py` 讀 `_md/`。
- 給另一個 agent 的契約與圖：`00-總計畫-給Claude.md`。

週報 Markdown 裡的數字不用來當係數。原始 PDF、msg、xlsx 沒有被修改。

## 1. 這四個字不是同一件事

| 字 | 是什麼 | 這份資料夾裡有沒有 |
|---|---|---|
| `QO` / `86` | 只報價。命中率的分母 | 沒有報價母體。贏單路徑裡出現 10 個 `86` 字串，列在 `combo_results.json` 的 `qo_strings_in_won_paths_not_used`。不用它們當分母 |
| `SO` / `88` | 報價之後有銷售額 | 有。`_md/` 路徑裡 388 張不重複的 SO |
| `PO` / `1000` | 向 vendor 下的採購單 | 有，是履約檔，不是報價，也不是毛利 |
| 週報 `sales ($)` | 已入帳金額 | 有。沒有成本欄，所以不是毛利 |

兩份週報是同一本帳往前滾，沒有相加。

- `Weekly Report-12312025.xlsx`，表頭 2025-12-31。只用來對 2025 目標。
- `Weekly Report-09182026.xlsx`，表頭 2026-09-18。回歸只用這份月欄 B 到 N，13 個欄位日期，從 2025-09-23 到 2026-09-23。這些日期還沒有核對成財務月。

檔案櫃不是週報的底稿。Vast、SUSE、Canonical 有週報金額，沒有自己的 vendor 櫃。Microsoft 的週報金額是整本 OS 生意；檔案櫃裡帶 `SFT-MS` 的 SO 只有 6 張，不能拿來代表 Microsoft。Lightbits 有 10 張 SO，週報沒有金額列。`TSMC/` 是客戶案卷，裡面認得出廠商的料號已經歸到該廠商，沒有另造一家叫 TSMC 的軟體 vendor。

轉檔：本機 markitdown 0.1.6，沒有 Azure，沒有圖片模型。`_md/_convert-log.tsv` 記 1,600 筆成功、3 筆失敗。失敗是沒有副檔名的 OSNEXUS 檔、一份 Unexpected EOF 的 Red Hat PDF、一份沒有 PDF `/Root` 的 2020 Weka PDF。143 個 Markdown 的路徑裡沒有 SO 號，沒有進組合表。

## 2. 兩張圖在畫什麼

根目錄兩張 `SW Monthly Rev. and Qty` 都是 `Total overview` 的圖。橘柱是 Microsoft，紫柱是 Microsoft 以外的全部，不是「儲存軟體」。藍線把各家 qty 加在一起。Microsoft 的 qty 是套數；Weka、Vast、Qumulo、OSNexus 的 qty 是授權或容量單位；DDN 的 qty 接近台數。這三個不能加成一條線。

2026-02-23 那一欄，總銷售是 16,185,255.97，其中 Vast 是 14,684,938。該欄 Other qty 裡 Vast 的數量是 292,800。這是 Huber 回歸唯一標出的異常月，見第 5 節。它不是硬體出貨台數。

週報自己的「12 個月合計」是 `SUM(C:N)`，不含 B 欄。圖的橫軸卻是 B 到 N。所以 `Total overview!O8` 不是圖上全部柱子的和，也不是 2026 日曆年。回歸用的是圖上那 13 欄，13 欄總銷售加總是 52,616,462.65。各 vendor 列加總與這條總額的最大差距是 1.9e-9，是浮點誤差，不是另一筆生意。

`Total overview` 的 P 欄才是腳本沒有重算、但公式看得到的另一種切法：`Non Storage Total` 與 `Stotage Total`。後者是錯字。這條「非儲存」把 CTERA 和 Pica8 算進去了，CTERA 在目標表被放在 Edge。不要把紫柱讀成儲存，也不要把 P 欄讀成嚴格的 OS。

`RedHat/Red Hat PO/Redhat PO request.docx` 寫的是：產線不必先備 SFT，等 system order 要出貨才提供 SFT POD。`Fulfillment process WekaIO.docx` 沒有正文。

## 5. 四個回歸

樣本都是 2026-09-18 週報的 13 欄。t 是欄位序 0 到 12，不是日曆月的名稱。n=13。係數描述這個窗口，不是因果，不是命中率，不是毛利。非零月少於 4 的 vendor 沒有做直線，包括 SUSE、Red Hat、CTERA、Scality、Quantum、Pica8、Hammerspace、Xinnor、Monitize360。SteelDome 全是 0。

### 線性

`sales = a + b t`。斜率的 95% 區間如果跨過 0，這個窗口看不出穩定的上升或下降。

總額的斜率是每欄 +222,239，R² = 0.038，斜率 p = 0.53，區間從 -523,429 到 +967,908。看不出趨勢。

扣掉 Vast 和 DDN 之後的合計，斜率是每欄 +64,456，R² = 0.052，p = 0.46，區間仍跨過 0。底線也看不出變陡。

唯一斜率區間沒有跨過 0 的是 GRAID：每欄 -20,799.56，R² = 0.488，p = 0.0079，區間 -34,941 到 -6,658，13 欄裡 12 欄非零。GRAID 在這個窗口是往下的，儘管 2025 全年目標表上它過了 1,000,000 的目標。Microsoft 的斜率 p = 0.27。Weka p = 0.53。Vast p = 0.52。DDN p = 0.70。

### 平面

兩個自變數：欄位序，以及該 vendor 自己的 qty。

Microsoft `SFT` 金額對 `SFT` qty 與時間。R² = 0.756。qty 的係數是 189.57 美元每 1 個 qty，p = 0.00043，區間 107.56 到 271.57。時間項 p = 0.077，區間跨過 0。在 Microsoft 內部，金額跟著套數走，不跟著時間走。

Weka 金額對 Weka qty 與時間。R² = 0.704。qty 的係數是 27.99，p = 0.00078，區間 14.87 到 41.11。時間項 p = 0.30。在 Weka 內部，這 13 欄的金額也跟著它自己的 qty 走。

這沒有把藍線救回來。兩家的 qty 不是同一個單位，也不是伺服器台數。Vast 那種 292,800 的數量沒有放進這張平面。跨 vendor 加總的 qty 仍然不是管理指標。

### 規律

零月比例是 13 欄裡金額為 0 的比例。變異係數含 0 的月份，所以斷斷續續的 vendor 會很大。一階自我相關是這一欄對上一欄。

| GRAID | 0.08 | 1.36 | 0.08 | 1,108,992 |

其餘 vendor 的零月比例是 0.77 或更高。沒有一家的 AR(1) 顯示「這個月會穩定帶到下個月」。Microsoft 是每月都有、波動最小的一條。Vast 的金額和最大，但有接近一半的月份是 0。

Ridge 的 y 是月份總額，x 是各 vendor 金額。總額就是各家之和，所以這不是「誰造成了總額」。係數是美元每 1 個標準差。全 0 的 SteelDome 先拿掉。一家若在某個懲罰係數下，絕對係數低於當下最大家的 5%，記為退場。

懲罰放到 1,000 時還排在前面的是 Vast、OSNexus、DDN、CTERA、SUSE。Quantum、Qumulo、GRAID、Xinnor 在懲罰為 0 時就低於 Vast 峰值的 5%，因為它們的金額波動比 Vast 小，不是因為回歸判定它們沒有生意。GRAID 的直線向下是另一個結果，不要跟這條 Ridge 混讀。

### 不正常

Huber 直線（c = 1.345）擬合 13 欄總額。殘差要大於 3×(1.4826×MAD) 才標出。這條規則只標出 2026-02-23：殘差 13,410,348.73，該欄總額 16,185,255.97，最大 vendor 是 Vast，14,684,938。

## 6. 命中率與毛利，這次都沒有估計

命中率要的方程式是：

`logit P(88|86) = β0 + β1·報價含 SFT 行 + β2·只有硬體 + β3·vendor + β4·折扣 + β5·業務`

現在沒有死掉的 `86`，沒有行項目，沒有業務。係數不存在。

`combo_results.json` 裡有 1,177 列 `qo_rate_table_unfilled`。每一列的 `qo_count` 和 `so_over_qo` 都是 null。下面只摘贏單裡已經數得出的組合，比例欄故意空白。這不是 0%，是未知。

毛利要的方程式是：

`毛利率 = γ0 + γ1·折扣 + γ2·vendor + γ3·是否搭硬體 + γ4·單筆金額`

沒有售價對成本的母體，也沒有牌價或核準折扣帶，所以「最大毛利」沒有定義。不把 40,000,000 減掉已入帳叫做 margin。那個差叫做目標缺口，第 3 節已經列了。

TSMC 資料夾裡有一張 `Total Saling Price`，另有一張 WEKA SPA 寫 `Total SMCI Cost = 563,728.75`。那是 2021–2022 的個案，沒有放進回歸。

## 7. 每一家贏單裡的軟體與機器

完整的空比例表在 `analysis/combo_results.json` 的 `qo_rate_table_unfilled`。

## 8. 三個問題，分別能說到哪

**成交率為什麼低。** 這批檔案沒有量到成交率。能說的是已入帳的形狀：Microsoft 每月都有、金額平穩，但 2025 只是貼著 6,000,000 的目標；目標最大的 Weka 在 2025 是 7,539,614.67 對 15,000,000，2026 Q3 達成率 0.06；2026 的總額和 Q3 的 1.25 來自少數 Vast 月份，不來自一條變陡的底線。贏單檔案裡也看不到「一個軟體配一種機器就會成交」的比例。

**業務為什麼沒有誘因。** 沒有佣金辦法或 quota 權重，不能下這個結論。檔案裡只有兩件結構事實：目標表的 owner 不是業務；Red Hat 流程把 SFT 放在 system order 要出貨之後。這支持一個假設，軟體是硬體單之後的採購動作，不在成交當下的分數裡。假設不是證據。

**硬體為什麼不是解。** 週報沒有伺服器營收，也沒有 attach rate。藍線不是硬體。贏單裡機器與軟體的共現，最多只能說「這張已經贏的 SO 上同時寫了什麼」。Weka 有 57 張連機器型號都沒寫出來，多過任何一種機型。就算 `CSE-116TS-R706WBP5-N10` 是寫得出來的機器裡最多的，也只有 21 張，而且不知道有多少報價用了同樣的機器卻沒有變成 SO。

下一步仍是兩份匯出，沒有它們就不再估計：`86` 對 `88` 的行項目（文件號、日期、軟體料號、機器料號、金額），以及 SO 售價對 vendor 成本。
